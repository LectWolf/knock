# Knock 领域词表

这个文件定义**我们说的是什么**，以及**这些词不指什么**。改术语先改这里，再改代码。

读法：每个词两条——「定义」说它是什么，「不指」说它**不是**什么。
**界线比定义重要**：这个项目崩过的每一个混乱，都是有人把两个词的边界当成了同一件事。

状态值与失败码的**取值**以 `AGENTS.md` 的状态机表为唯一真相，本文件只定义概念、不复制表格。

## 0. 先看这张表：五样东西的关系

| 概念 | 活多久 | 属于谁 | 基数 | 一句话 |
|---|---|---|---|---|
| **Node 节点** | 长期（进程活着） | —— | 1 节点 : N 房间 | 别人家的机器，替你换地址，必要时替你转发 |
| **Room 房间** | 开门 → 关门（分钟级） | 某个节点 | 1 房间 : 1 门牌号 | 一次「门开着」的登记 |
| **Code 门牌号** | 与房间同生共死 | 房间 | 1 : 1 | 房间在那个节点里的短地址 |
| **Session 会话** | 敲门 → 断开 | 房间 | 同一时刻 ≤ 1 | 一次实际的连接尝试及其结局 |
| **Tunnel 通道** | 连通 → 断开 | 会话 | 1 : 1 | 真正搬 MC 字节的那条管子 |

三条推论，记住这三条就不会含糊：

1. **房间可以没有会话。** `waiting` 就是「有房间、没会话」。会话结束后房间通常还在，门牌号不变，
   同一个人可以再敲一次门。
2. **门牌号不属于人，属于房间。** 房间关掉它就失效。**同一串 6 位字符在另一个节点上可能是另一个房间。**
3. **节点不是「我们的服务器」，也不是「中继」。** 节点是机器；中继是这台机器在某种情况下的**角色**。

## 1. 拓扑与信任

**Node（节点）**
一台由用户自行托管的服务器进程，负责两件事：替房间交换候选地址（信令），以及在打洞失败时转发加密流量（中继）。
不指：某台云主机/物理机本身（机器是机器，节点是跑在上面的服务）；也不指客户端。

**Relay（中继）**
节点的一种**角色**：在两端打不通时，替它们转发密文，节点自己解不开内容。
不指：节点（节点是中继的宿主，不是中继的同义词）；不指「我们提供的服务」（我们不提供）；不指一条路径。

**Pin（指纹）**
节点长期公钥的哈希截断（8 字节），写在节点码里，用来确认「连上的确实是我以为的那台机器」。
不指：密码（它不是秘密，可以公开）；不指「连接加密用的密钥」（加密在两端之间做，与 Pin 无关）。

**Label（标签）**
节点自选的 2 字节短名，编码后 4 字符，用来把邀请串从 35 字符压到 11 字符。
不指：唯一标识（不同节点可以撞名，撞了让用户选）；不指中心分配的编号（没有任何人在分配）。

**NodeCode（节点码）**
一串自描述编码，装着节点地址、端口、标签、Pin。**任何人拿到它就能把这个节点加进客户端。**
不指：门牌号（`Code` 永远只指门牌号）；不指邀请串（邀请串 = 节点码 + 门牌号）。

**NodeList（节点列表）**
一份静态清单，用于**发现**节点。可以是内置的、用户自定义 URL 的、或手动添加的。
不指：解析机制（不在列表里的节点，用完整节点码照样能连）；不指在线状态（状态靠探测，不靠列表）。

## 2. 房间与访问

**Room（房间）**
房主在某个节点上的一次登记：「我是谁、我的服务在本机哪个端口、我还在等」。
它是有生命周期的对象，开门时创建，关门时销毁。
不指：Minecraft 服务器进程（那个进程可以一直开着，房间是一次联机登记）；不指一次 TCP 连接；不指节点。

**Code（门牌号）**
房间在**它所属的那个节点内**的短地址，6 字符，人可手输。
**它只是地址，不是凭据**——30 bit 的熵当不了密码，安全靠限速与 TTL。
不指：密码；不指全局唯一的房间号；不指邀请串（它是邀请串的一部分，不是全部）。

**Invite（邀请串）**
把「去哪敲门」和「敲哪个门」合在一起的那一串东西，对方粘一次就能连。
完整邀请 = 节点码 + 门牌号；短邀请 = 标签 + 门牌号；只有门牌号时依赖对方已知的节点。
不指：节点码（节点码是「加个节点」，不是「敲这扇门」）；不指持久凭据（房间关了它就废了）。

---

## 3. 连接与路径

**Session（会话）**
从房客敲下门牌号那一刻开始，到任一方断开为止的**一次连接尝试及其结局**。
一个房间同一时刻最多有一个活动会话；会话失败或结束后，房间仍然可以是「门开着」。
不指：房间（房间是登记，会话是尝试）；不指 Tunnel（会话在打洞阶段还没有通道）；
不指「一次 MC 登录」（那是 MC 自己的概念）。

**Peer（对端）**
隧道另一头的那个**客户端**。房主视角的对端是来客，来客视角的对端是房主。
不指：Minecraft 服务器；不指节点；不指「对方玩家」（同一个人可能有多个客户端进程）。

**Candidate（候选）**
一个「也许能连上对端」的地址组合（IP:端口 + 来源类型：局域网 / 公网映射 / 端口预测 / 中继），
用来逐个尝试。
不指：节点的地址（节点是信令方，不是候选）；不指最终选中的那条路（那是 Tunnel 的事）。

**Tunnel（通道）**
会话连通之后，真正承载一条 MC TCP 流的加密双向管道。它可以跑在直连上，也可以跑在中继上。
不指：中继本身；不指会话（会话是生命周期与状态，通道是数据通路；`punching` 阶段会话存在、通道不存在）。

## 4. 状态与失败

**ConnState（连接状态）**
客户端唯一的状态来源，一个 7 值枚举，描述「当前这次连接处在哪一步」。界面只渲染它，不推断进度。
不指：UI 页面或视图（页面是状态的投影，不是状态）；不指网络层的真实情况（它可能滞后）；
不指进度百分比（没有百分比这个东西）。

**FailReason（失败原因码）**
挂在 `failed` 状态上的载荷，决定给用户看哪一句话。取值见 `AGENTS.md`。
不指：一个独立状态（它只存在于 `failed` 里）；不指日志里的错误字符串（日志可以很详细，这个只给用户看）；
不指「所有错误」（正常关门不是失败）。

## 5. 边界自检：拿这几个问题去问代码

**Q1. 房主开门 → 朋友连上 → 朋友掉线。此刻房主是什么状态？房间还在吗？门牌号还能用吗？**
房主回 `waiting`，**不是 `failed`、不是 `idle`**；房间还在；门牌号不变；朋友可以再敲。
（房客那一侧才是 `failed(host_offline)`。**这条最容易被写成两边都 `failed`。**）

**Q2. 房主换一个节点重新开门，门牌号碰巧还是 `A7K2M9`，这是同一个房间吗？**
不是。门牌号是节点内的短址，换了节点就是另一个房间。

**Q3. 房客粘了完整邀请，结果 `code_not_found`。谁错了？**
可能两件事：邀请里的节点码指错了节点，或者房间已经关了。所以文案必须同时覆盖两种
（「门牌号不对，或者已经过期」），不能只写"过期"。

**Q4. 会话在 `relay` 状态时中继断开，两侧分别进什么状态？**
房客 → `failed(relay_unavailable)`；房主 → 回 `waiting`（房间还开着，还能再接待）。

**Q5. 房主开门后 30 分钟没人来，这算 `failed` 吗？**
不算。超时关门是正常结束，回 `idle`，文案是「门开太久了，已经关上」。**`failed` 只给真正的失败。**

**Q6. `direct` 和 `relay` 的区别是「连没连上」还是「走哪条路」？**
走哪条路。两者都是连上了，只有 `direct` 是直连。界面上两者的差别只有一句括注。

**Q7. 界面上的转圈动画应该在 `punching` 时启动吗？**
不该由界面判断。界面拿到 `punching` 就渲染 `punching` 该有的样子；不许写 `if (打洞中) 显示转圈`。

## 6. 对外用语（所有用户可见文案的唯一来源）

**状态 → 文案**

| ConnState | 用户看到 |
|---|---|
| `idle` | 输入门牌号（房主页：点一下开门） |
| `creating` | 正在开门… |
| `waiting` | 把门牌号给他：`A7K2M9` |
| `punching` | 正在敲门… |
| `direct` | 门开了 |
| `relay` | 门开了（绕了点路，会慢） |
| `failed` | 没人应门（标题）+ 下面接原因 |

**FailReason → 文案**

| FailReason | 用户看到 |
|---|---|
| `code_not_found` | 门牌号不对，或者已经过期 |
| `host_offline` | 门开着，但屋里没人（房主没开服） |
| `blocked_by_firewall` | 门被挡住了（本机防火墙） |
| `symmetric_nat` | 两边都出不去（对称 NAT），需要中继 |
| `relay_unavailable` | 绕路也走不通，稍后再试 |

**动作与对象 → 对外词**

| 内部概念 | 对外说法 | 备注 |
|---|---|---|
| Room 创建 | **开门** | 房主动作 |
| Room 关闭 | **关门** | 主动结束，不是失败 |
| Room 超时 | **门开太久了，已经关上** | 不是失败 |
| Code 输入 | **敲门** | 房客动作 |
| 失败重试 | **再敲一次** | |
| Node | **驿站**（暂定，待确认） | 门开在驿站上，驿站帮忙指路 |
| NodeList | **驿站列表**（暂定） | |
| 经中继连通 | **绕了点路** | 不说「中继」 |
| 中继不可用 | **绕路也走不通** | 不说「中继服务器」 |

**禁用词**（在界面、提示、错误文案里一律不出现）：
连接、断开、握手、隧道、通道、端口、IP、P2P、打洞、NAT 类型、会话、房间、节点、加速器、VPN、翻墙、梯子。

**唯一的例外**：`symmetric_nat` 的文案「两边都出不去（对称 NAT），需要中继」是 `AGENTS.md` 定稿，
里面出现了「中继」和「NAT」两个词，保留不动；除此之外所有文案都不出现这两个词，一律说「绕路」。

**错误文案结构**（三行，不许只有一行）：
1. 标题：`没人应门`
2. 原因：上表对应那一句
3. 动作：一个可点的按钮（`再敲一次` / `换个驿站` / `检查防火墙`），失败页不许是死胡同。
