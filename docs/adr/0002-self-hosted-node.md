# ADR-0002 无中心部署：自托管节点、紧凑编码、可插拔节点列表

> 状态注记（2026-10-28）：本文第 6 条关于「一个房间一条通道」的表述已被 [ADR-0004](./0004-multi-guest-and-control-channel.md) 修订。其余结论仍然有效。

- 状态：accepted
- 日期：2026-10-28
- 取代：ADR-0001 中「服务端是我们运营的 hub」与「SQLite 存房间/配额/计费」两条。Go、Rust 核心、Tauri 界面仍然有效。

## 背景

ADR-0001 假定有一个我们运营的中心服务：它持有房间表、发 6 位码、做配额与计费。产品负责人决定改成
**不运营任何中心服务**：节点由用户自行托管，项目只发布代码。这个决定要同时回答三个问题：

1. 房间登记放在哪？（没有中心，谁记住「A7K2M9 指向谁」）
2. 6 位码怎么保证能被对方解析？（6 字符放不下地址）
3. 节点怎么被发现？（用户怎么找到可用的节点）

## 决定

### 1. 节点 = 信令 + 中继二合一

一个节点干两件事：为房间交换候选地址（信令），以及在打洞失败时转发加密流量（中继）。
没有中心服务，候选地址交换只能由节点承担，因此**房间登记表长在节点上**。

推论：**门牌号是「某个节点上的」房间短址，脱离节点无意义**。这是本 ADR 最重要的语义决定，
`GLOSSARY.md` 里的 Room / Code / Session 三者边界全部由它推导。

### 2. 节点编码自描述，不依赖任何列表

编码里直接带地址、端口与指纹，所以一个刚装好的节点**不需要出现在任何列表里就能被使用**。
典型长度 29 字符（仅 IPv4），Crockford Base32（大小写不敏感、去掉 `I L O U`，便于 OCR 与报障）。

布局 v1（小端）：

| 字段 | 字节 | 说明 |
|---|---|---|
| version + flags | 1 | 高 4 bit 版本；低 4 bit：有 v4 / 有 v6 / 有域名 / 允许中转 |
| label | 2 | 节点自选标签，编码后 4 字符，用于短邀请；**不是中心分配** |
| address | 4 / 16 / 1+len | 按 flags 三选一：IPv4 / IPv6 / 域名 |
| port | 2 | 节点主端口 |
| pin | 8 | 节点 Ed25519 公钥 SHA-256 的前 8 字节（64 bit） |
| crc8 | 1 | 输错时能明确说「码不对」，而不是超时 |

| 场景 | 字节 | 字符 |
|---|---|---|
| 仅 IPv4 | 18 | 29 |
| 仅域名 `relay.example.com` | 32 | 52 |
| 仅 IPv6 | 30 | 48 |
| 双栈 v4+v6 | 34 | 55 |

**这些码不是给人手输的**，是复制/扫码用的；**6 位门牌号仍然是人手输的那一个**。
指纹截断到 8 字节是刻意的：伪造需要 2^64 次哈希，而这个截断省掉约 22 个字符。

### 3. 三级邀请

| 形态 | 样例 | 长度 | 何时用 |
|---|---|---|---|
| 完整邀请 | `<节点编码>.A7K2M9` | 36–62 | 首次配对；或对方没有该节点 |
| 短邀请 | `04HM.A7K2M9` | 11 | 双方都已添加该节点（高频） |
| 只有门牌号 | `A7K2M9` | 6 | 双方都只添加过一个节点 |

短邀请里的 `04HM` 是编码中 `label` 字段的 Base32 形式。解析：0 个匹配 → 提示发完整邀请；
1 个 → 直接用；多个 → 列出来让用户选。**长度只在首次昂贵，而首次是低频的。**

> **修正（实现时定）**：完整邀请原设计是"节点码直接拼门牌号、不用分隔符"，靠"先解 2 个字符拿 flags
> 再算长度"来切分。那套算术要在两种语言里各写一遍且无声错位风险高，所以改成用 `.` 分隔，
> 多花 1 个字符换确定性。**字节布局与金标向量以 [`spec/invite-v1.md`](../../spec/invite-v1.md) 为准**，
> 该文件带 `spec/invite-v1.tsv`，Rust 与 Go 的测试读同一份。

### 4. 列表只管发现，不管解析

`nodes/` 下是一份静态 JSON，靠 PR 提交、靠 CI 校验，不跑任何服务。字段：
`id`（= pin 的 Base32）、`name`、`relay`（是否允许数据中转）、`endpoints`、`limits`、`note`。

- `id` **自证**：客户端连上后校验节点公钥指纹与 `id` 一致，不一致直接断开并报「节点被替换」。
  → 列表被篡改最坏是浪费时间，**不能冒名**。这是列表**不需要签名、也不需要维护者可信任**的原因。
- 列表**只放静态能力**，不放运行状态（延迟、占用由客户端探测与节点自报获取）。
- 国内访问 GitHub raw 不稳：客户端内置快照 + 支持镜像 URL + 支持自定义列表 URL。
- 公开发布等于公开节点主人的 IP：必须显式勾选，允许只发布域名。

### 5. 绕路确认是偏好，不是状态

7 态状态机不动。设置项三选一：`总是自动中转`（默认，与 AGENTS.md 一致）/ `每次询问` / `从不中转`。
选「每次询问」时，打洞失败后 transport 仍停在 `punching`，对外抛一个 **RelayOffer 事件**（事件不是状态），
用户选「绕路」→ `relay`，选「不」→ `failed(relay_unavailable)`。

## 被否掉的备选

- **中心 hub**（ADR-0001 原方案）：要我们出机器、出带宽、担滥用责任，且和「开源、不提供服务器」冲突。
- **必须上列表拿 ID 才能用**：把「发现」和「解析」耦合成一件事，新节点要等列表更新才能用。
  自描述编码已经把解析这件事解掉了，别再装回来。
- **只做手动候选交换（手抄 SDP 式）**：零基建，但体验差到不能作为主路径。留作将来的应急模式。
- **用 DNS TXT 做节点解析**：节点主人要有域名且会配记录，覆盖面太小；作为将来对「短码」的优化再说。
- **给列表签名**：指纹钉扎已经保证了「冒名不可能」，签名只能多防一层「列表被替换」，
  而那一层的收益是「少浪费一次时间」。不值得为它引入密钥轮换与分发。
- **把房间登记放在 DHT**：延迟、可用性、以及被当免费基础设施的风险都不划算，MVP 不碰。

## Consequences

1. **新用户开箱需要一个「第 0 台」节点**，否则连房都开不出来（信令也在节点上）。seed 列表留空但支持 URL
   与自定义列表；文档必须写清「这是一份索引，不是我们的服务」。
2. **没有计费，也没有配额服务端**：配额变成节点本地配置（最大会话、每房间带宽），符合自托管语义。
3. **节点是两件事**：`iroh-relay`（Rust 二进制）+ 我们的房间/配额 API（Go），装成两个 systemd 服务。
4. **滥用治理前移到节点**：没有中心可封人，节点必须自己有限速、房间上限、`code_not_found` 查询限速。
5. **门牌号的安全性依赖房间上限与限速**：6 字符约 30 bit，能在公网节点上被枚举，必须靠限速与 TTL 挡住。
6. **这是「一个房间一条通道」边界仍然成立的最后一个支点**：节点只做「两个持码端点之间转发」，
   从不主动外连任何目标，所以它不是开放代理——这个性质要在协议与文档里写死。
