# ADR-0003 传输底座：iroh（打洞 + 中继兜底 + QUIC 一套解决）

- 状态：accepted
- 日期：2026-10-28

## 背景

隧道核心要完成：MC 的 TCP 流 → 用户态可靠传输（UDP）→ 打洞直连 → 失败自动退到节点中继 → 对端还原成 TCP。
客户端不许要管理员权限，所以「伪装 TCP」「改系统网络配置」这一派全部出局。
自己从零写，等于把 NAT 类型探测、端口预测、路径切换、中继协议、拥塞控制全部揽下来——
**真正的工作量不在写，而在「某种路由器/某种运营商下不工作」的排查上。**

## 决定

**传输底座用 `iroh` 1.x**（MIT OR Apache-2.0），不自己实现打洞与中继协议。

选它的理由逐条对得上需求：

- 它就是「QUIC 流给上层，底层打洞，打不通自动退回中继」——与 ADR-0002 的节点模型同构。
- 中继只按 `EndpointId` 转发密文，无法解码内容：满足「节点看不到流量」。
- 中继协议是 DERP 的改良版：我们论证过的形状，别人已经实现并跑了几百万次下载。
- `RelayMap` 就是一个节点列表结构，直接对应客户端节点列表。
- 中继可跑在 **HTTP 或 HTTPS** 上：自托管节点没有域名也能用，正好配合「编码带 IP + 端口 + 指纹」。
- `iroh_relay::tls` 提供自定义 TLS 校验：自签证书 + 指纹钉扎可做。
- 依赖里带 `portmapper`：**UPnP / NAT-PMP 自动端口映射**，这是第三条路（见下）。
- 身份 = Ed25519 公钥，`EndpointId` 即身份，天然满足「指纹钉扎」。

**必须显式关掉它的默认值**：`RelayMode::Custom(RelayMap)` 只用我们列表里的节点，
并关掉 `DnsAddressLookup`。否则等于又依赖了 n0 的中心服务，与 ADR-0002 冲突。

### 第三条路：自动端口映射

房主开门时先尝试 UPnP / NAT-PMP / PCP 把 UDP 端口映射出去。成功则对方**直接连**，
压根不需要打洞；失败就回落到打洞，零成本。**它不产生新状态**——映射成功也报 `direct`，UI 只说「门开了」。

## 被否掉的备选

| 候选 | 否掉原因 |
|---|---|
| 自己写（`quinn` + 自写信令） | 编码能更短（8B 指纹足够），但 NAT 边界情况是月级调试成本；先用成熟的，等真被卡住再说 |
| libp2p（DCUtR + Circuit Relay v2） | 能力齐全但抽象层过多、PeerId 编码长、引入整棵 Kademlia |
| webrtc-rs | ICE-TCP 兜底弱，SCTP 开销与调试面大 |
| tsnet / headscale | 要协调服务器，等于把中心装回来；且是 VPN 形状，撞产品边界 |
| frp / rathole / ngrok 类 | 无 P2P，全靠中转带宽 |
| `udp2raw` / `phantun` 伪 TCP | 要 WinDivert / raw socket = 管理员权限。**客户端侧永久否决**；节点侧允许（见 AGENTS.md 权限边界） |

## Consequences

1. **邀请串长度不受影响**：iroh 要 32 字节 `EndpointId` 才能拨号，但邀请串里只放**节点**身份；
   房主/房客的 `EndpointId` 由节点的房间接口在敲门时交换。29 字符的码仍然成立。
2. **节点是两个进程**：`iroh-relay` + Go 房间 API，安装脚本装两个 systemd 服务。好处是两者解耦，将来能换掉任一个。
3. **`iroh-relay` 没有「信令但不搬运数据」的开关**：「只打洞」模式要自己加（fork 或前置拦截）。量不大，但要算进工期。
4. **`iroh-relay` 没有按人限速/配额**：拥挤度与每房间带宽上限靠 OS 层 `tc`/`nftables` 按 IP 限速，或 fork 加计数器。
   「握手自报占用」需要我们自己补一个统计层。
5. **依赖树不小**（rustls / axum / noq），客户端二进制变大——Tauri 壳本来就大，可接受。
6. **骨架阶段完全不碰它**：第 3 步用假 transport 证明状态机与接口，接 iroh 是之后的事，且不透传进状态机。

## 实现进展（2026-10-28）

**已经落地**：`client/src-tauri/src/pipe.rs` 用 iroh 1.4.1 把 TCP 与 QUIC 双向流对接，
`tests/iroh_loopback.rs` 用**真的** QUIC 连接（`RelayMode::Disabled` + 环回地址，不碰公网、不碰中继）
跑通三件事：字节往返、多条连接并存、256 KB 大块数据完整。

依赖只开两个 feature：`tls-ring` + `portmapper`；不开 metrics，也**永不**回落到 n0 公共中继。

**还没接上的那一环**（下一轮）：房间接口目前只发门牌号，没有交换 `EndpointId`。
按 Consequences 第 1 条，房主开门后必须把自己的 `EndpointId` + 直连地址发布到房间上，
房客查码时取回——这一步叫 announce。它牵出两个协议问题，需要在写代码前定下来：

1. **谁能 announce**：只有持有「开门时拿到的那把房间令牌」的人能写。令牌由 `POST /rooms` 一次性返回，
   不入库明文（存哈希）。否则任何人都能往别人的房间里塞假地址，把人骗去连自己。
2. **候选地址怎么给**：房主 announce 一组直连地址（可能多个）；房客取回后逐个试。
   是否允许房主在 `waiting` 期间**重新** announce（换网络、换端口）——允许，但要限次。

## 加密边界（"中间服务端可不可信"）

**端到端加密，节点看不到内容。** iroh 每条连接都是 QUIC + TLS 1.3，
而每个端点的身份**就是**它自己的 Ed25519 公钥——自签名证书，没有 CA、没有证书链。
节点（信令 + 中继）只做两件事：换地址、转发密文。

它能看到：谁和谁在通话、什么时间、多少字节、两端 IP。
它看不到：MC 的字节流。没有任一端私钥就没有解密路径，节点被完全控制也一样。

另外两道锁：

- 客户端必须先用自己手里的 pin 校验节点自报的公钥（SHA-256 前 8 字节）才肯继续；
- 房主的 `EndpointId` 由房主自己签名，节点改不了。

所以节点能做的上限是：**拒绝服务 + 元数据分析**。这符合产品边界里"不运营中心服务"的假设。

## 中继：接哪些流量、有多大

- **只有打洞失败才走中继**；打通了就是点对点，节点完全不参与。
- MC Java 单人流量典型 20–150 kbit/s，峰值几百 kbit/s。10 Mbps 上行大约能同时养 50–100 人。
- 中继转发的是密文，节点既不能缓存也不能解包。

## 中国网络与「HTTP 被拦截」

- **中继连接不是明文 HTTP**：iroh-relay 走 TLS 1.3，先做 HTTP/1.1 upgrade，
  之后是自定义二进制分帧，全程在同一条 TLS 连接里。DPI 看到的是 TLS。
- 真正会被"上游拦截并返回别的页面"的是**明文 HTTP**。所以定两条规矩（两侧代码都有测试钉着）：
  1. 房间接口将来必须上 TLS；今天的明文只用于本机/内网验证。
  2. `relay_url` 公网必须 `https://`，只有环回地址才允许 `http://`。
- 若中继地址本身被墙：打洞仍是主路径，中继是兜底而非唯一。

## 路径选择：一次决定，不中途换轨（2026-10-28）

**规则**：能打洞就直连，打不通就中继；落定后整场会话锁死该模式，
**不启用「直连断了、中继悄悄接上」**。

**为什么能强制而非尽量**：直连阶段房客端点用 `RelayMode::Disabled` 绑定，
端点与中继之间没有连接——路径断了没有载体接班。要换轨只能重新绑定，
那是一次新的决定，不是旧连接的续命。

**丢包保护不受影响**：重传、拥塞控制、乱序重排是 QUIC 的职责，与路径切换无关。
禁掉换轨不会让 P2P 更容易"掉线"，只会让彻底不通时诚实地断。

**代价**：

- 直连失败要多花 3–5 秒才落到中继；
- 直连中途失败 = 会话结束（MC 自己报「连接已丢失」）；状态机不因此迁移，
  因为 7 个状态里没有「掉线」，`direct` 保持终态是正确的；
- 房主必须一次性绑定带中继的端点（端点身份要 announce），这不破坏规则：
  房客试直连时没有中继，房主有中继也接不上来。

**怎么判定走了哪条**：`conn.paths()` → `Path::is_relay()`，在首字节通过时取一次快照。
不靠"对端 IP 像不像房主"——走中继时对端列表里也可能写着房主的真实 IP。
