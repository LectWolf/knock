# ADR-0001 技术栈：Tauri 2 + Vue 3 + TS / Rust 隧道核心 / Go 服务端 / SQLite

> 状态注记（2026-10-28）：本文的「一个房间一条通道」已被 [ADR-0004](./0004-multi-guest-and-control-channel.md) 修订为「一扇门可多人，每人一条数据通路」。其余结论仍然有效。

- 状态：accepted，**部分条款已被 ADR-0002 取代**
  （「服务端 = 我们运营的 hub」→ 用户自托管节点；「SQLite 存房间/配额/计费」→ 房间在内存、SQLite 只做节点本地存储。
  界面栈、Rust 核心、Go 这三条仍然有效。）
- 日期：2026-10-28

## 背景

Knock 是 Minecraft Java 版联机工具：房主开门拿到 6 位门牌号，朋友敲码进服。硬约束是
**不装虚拟网卡、不要管理员权限、默认只代理 TCP `25565`、一个房间一条通道**；连接必须
打洞直连优先、失败自动降级到自建中继，两条路都得走通。平台 Windows 10/11 优先，macOS 其次。

这些约束决定了选型的主要矛盾：**安装体积与免管理员**（排除重型运行时）、
**长期维护的网络核心**（要有内存安全与成熟的 async/IO 生态）、
**服务端的运维熟悉度**（中继是带宽型服务，得能快速上线和扩容）。

## 决定

| 层 | 选型 | 关键理由 |
|---|---|---|
| 客户端界面 | Tauri 2 + Vue 3 + TS | 复用系统 WebView，安装包 10 MB 级；与 `03-桌面应用/caiwu` 同栈，界面作者已有肌肉记忆 |
| 隧道核心 | Rust，位于 `client/src-tauri` | 打洞、候选交换、多路复用是长期演进的代码，放 Rust 拿到内存安全 + tokio/quinn 生态 |
| 服务端 | Go，位于 `server/`（`cmd/hub`） | 与 `02-站点与服务/MCII-日本主节点` 同栈；UDP 中继用 `net`/`gnet` 级别的代码就能写，goroutine 模型处理每房间一对连接很直接 |
| 存储 | SQLite | MVP 单机足够；房间、配额、计费都是低写入量小表，不引入 Redis |

补充两条**同样是决定**的边界：

1. **隧道核心与 UI 同进程**，通过 Tauri 的 command/event 通信，不做 sidecar 子进程。
   理由：状态机只有一份（见 AGENTS.md 硬规矩 1），sidecar 会引入进程生命周期、崩溃重启、
   版本错配三个额外故障面，而这三种故障在产品里都是"用户看到门打不开但不知道为什么"。
2. **协调与中继在 MVP 是同一个 Go 二进制，但代码分属 `rooms` 与 `relay` 两个包**，
   彼此只通过接口调用，不允许共享内存态。理由见「Consequences」第 3 条。

## 被否掉的备选

**Electron + Node/TypeScript 隧道核心**（最主要的竞争者）
否掉的原因不是体积本身，而是核心代码形态：打洞需要同时管理 UDP socket 的源端口保持、
候选地址收集、超时重试与并发状态迁移，Node 的 `dgram` 在这些点上要自己垫一层，长期维护成本高于
Rust；而"Rust 核心 + Electron 壳"又退化成现在这个方案的超集（多 100 MB 换取 Chromium 一致性）。
代价承认：放弃 Chromium，界面的跨平台一致性依赖 WebView2/WKWebView 两个实现，
CSS/JS 的边角差异要自己在 Windows 与 macOS 上各验一遍。

**Wails（Go 写界面后端，全栈统一 Go）**
有真实吸引力：一种语言覆盖客户端与服务端，中继协议的类型可以共享。否掉的理由是
打洞与多路复用在 Go 里同样要手写，而 Rust 侧 `quinn`/`snow`/`socket2` 的现成件更齐；
另外 Wails 的 Windows WebView2 绑定与打包链路比 Tauri 2 小众，出问题时能搜到的答案少一个数量级。
这不是技术判断上的"不能"，是风险预算判断：客户端是整个产品唯一必须长期迭代的复杂件，选生态厚的。

**原生 .NET（WinUI 3 / WPF）或 Avalonia**
Windows 上体验最好，但 macOS 是二线平台，Avalonia 的成熟度与设计还原度不足；
且隧道核心要用 C# 重写，等于放弃 Rust 生态。

**纯 Web 前端 + 本地守护进程（浏览器打开页面，后台跑一个 daemon）**
免去 GUI 框架，但用户要装一个没有窗口的守护进程、再记住一个本地地址，两条安装路径，
和"不要管理员权限、点一下就好"的产品口径正面冲突。

**Rust 写中继服务端**（与隧道核心同语言）
技术上更优（同协议结构体可共享，零 GC）。当前否掉：中继是运维问题多于算法问题，
Go 的上线/抓包/热重启/单文件部署经验在现有节点上已经跑熟，MVP 阶段迭代速度优先。
**重估触发条件**：单台中继持续跑满 1 Gbps 且 p99 抖动超标，或需要按包做细粒度限速时，重开此议题。

**现成的打洞/组网库（libp2p、Tailscale/wireguard-go 式方案）**
与产品边界冲突：它们的目标是虚拟网段/全流量代理，我们要的是"一个端口一条通道"。
引入它们会带来 TUN 设备与管理员权限，直接违背硬约束。

**PostgreSQL / Redis**
MVP 是单机、房间数据可丢可重建、写入量是每分钟个位数，两者都是纯运维负担。
代价承认：SQLite 是单写者，见 Consequences 第 2 条。

**QUIC 作为隧道唯一传输**
不否掉，但不在本 ADR 里定死。ADR-0002（隧道协议）再定 QUIC 与裸 UDP + 自定义可靠层的取舍；
本 ADR 只保证 Rust 核心有能力两种都实现。

## Consequences

1. **WebView2 是外部运行时依赖。** Windows 11 自带，Windows 10 绝大多数机器随 Edge 更新已装，
   但不保证。打包时用 Tauri 的 bootstrapper 模式（联网小体积）还是 offline installer（+100 MB）
   留到打包阶段决定，这条不影响现在的代码结构。
2. **SQLite 意味着协调服务是单实例、单写者。** 一旦要多活协调节点，必须先换存储或做分片，
   不能靠加进程解决。因此 `rooms` 包的所有写操作走同一个 `Store` 接口，
   未来换 Postgres 时只替换实现，不碰调用方。
3. **协调与中继的扩容形状不同，必须在第一天就分开。** 协调是低流量、强一致、单实例；
   中继是带宽型、无状态、要按地域多节点。所以 `rooms` 与 `relay` 分开建包，
   且**房间记录里只存中继节点的可达地址，不存进程内句柄**——这样中继节点以后可以独立部署，
   协调服务不需要改协议。
4. **客户端下载体积的预算给了界面层，不是核心层。** 隧道核心可以引 `quinn`、`snow` 这类依赖，
   但界面侧不允许引入重型 UI 框架（Element Plus 全量、Ant Design Vue 全量级别），
   以保住 10 MB 级安装包这个对外承诺。

## 重估触发条件

- 打洞成功率在真实网络样本上低于 60%，需要引入更复杂的 NAT 探测 → 重看隧道协议（ADR-0002）
- 单台中继带宽成为瓶颈 → 重看服务端语言（本 ADR 的 Rust 否决项）
- 房间量级需要多协调节点 → 重看存储（本 ADR 的 SQLite 项）
- WebView2 在目标用户群里缺失比例超过 5% → 重看客户端壳（Electron 项）
