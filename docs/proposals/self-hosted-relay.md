# 提案：去中心化——不运营公共中继，改为「自托管节点 + 编码」模型

- 日期：2026-10-28
- 状态：**待拍板**（未生效；生效后会以 ADR-0002 落在 `docs/adr/`，并修订 ADR-0001 与 AGENTS.md）
- 结论先说：**可行，建议这样做**，但有 5 个代价必须先接受，见第 5 节。

## 1. 提案内容（复述你的想法，作为讨论基线）

1. 项目**不自建/不运营**公共中转服务器。
2. 发布一个**可自托管的中转节点**：Linux 一键安装脚本 + Windows 版本；可配置端口；
   可选择「允许作为中转」或「只做打洞协调（信令）」。
3. 节点启动后生成一串**紧凑编码**，含：IPv4/IPv6 地址、端口、密钥。
4. 客户端粘贴这串编码即可**添加一个中转节点**；也可维护一个**节点列表**（可筛选是否允许中转、是否可用）。
5. 房主设好 MC 端口 → 开门 → 拿到 6 位门牌号。
6. 房主把「节点编码 + 门牌号」发出去；对方粘贴即可敲门。
7. 优先打洞直连；打不通且节点允许中转 → **询问是否绕路**；不允许 → 失败。
8. 全部开源，最后放 GitHub。

## 2. 先例核对（这个形状被验证过）

- **Tailscale DERP**：一个节点同时干两件事——NAT 打洞协调（信令）+ 打不通时的兜底转发。
  客户端拿到一份「DERP map」列表并本地持久化；DERP **只盲转已加密的包，看不到内容**；
  官方也允许自建 `cmd/derper`。→ 与本提案的形状几乎一一对应，说明设计成立。
- **e4mc**（MC 圈现成方案）：反向隧道把本地 MC 暴露出去，但**依赖作者自己出钱维护的中心服务器**——
  这正是你要避开的成本，也正是本项目的差异化空间。
- **frp / rathole**：可自托管，但没有 P2P，全靠中转带宽。
- **EasyTier / n2n**：自托管超级节点 + P2P 打洞，但目标是虚拟网段，与我们「一个端口一条通道」的边界冲突。

结论：形状不新、风险已知，可以走。

## 3. 由此确定的架构（三条是关键）

### 3.1 一个节点 = 信令 + 中继二合一

没有中心服务，就没人替你做候选地址交换。**信令必须由节点承担**：
房主把「门牌号 + 自己的候选地址」注册到节点，房客敲码时节点把双方的候选地址互相告知 → 双方打洞。
打洞失败时，同一个节点把双方的 UDP 包互相转发（TURN 式），连接继续。

推论：**节点不只是「中继」，它是这个房间的登记处**。所以
「门牌号」是**某个节点上的**房间短址，脱离节点无意义 → 邀请串必须同时携带节点身份。这与你的设计一致。

### 3.2 打洞打的是 UDP，不是 TCP

MC Java 用 TCP `25565`。**TCP 打洞成功率很差**（TCP 同时打开依赖命中时机，且多数 NAT 不配合）。
业界做法（Tailscale、ZeroTier、EasyTier、所有游戏联机工具）都是：

```
MC 客户端 → 127.0.0.1:25565（本机 TCP）
   → 隧道核心：TCP 流 → 用户态可靠传输（QUIC，跑在 UDP 上）
   → 打洞直连，或 经节点 UDP 转发
对端隧道核心：UDP → TCP 流 → 房主的 MC 服务端 127.0.0.1:25565
```

所以「只代理 TCP 25565」**不等于**「TCP 层转发」。隧道核心必须自带一个基于 UDP 的可靠层
（建议 QUIC / `quinn`，天然带 TLS 1.3 与多路复用）。这也反过来证明 ADR-0001 把隧道核心放 Rust 是对的。

好处：直连和中继**共用同一条 QUIC 连接**——中继只是 UDP 转发，QUIC 不用改；路径切换就是 QUIC 换路径。
这是本方案能做到"两条路都走得通"且代码只写一遍的原因。

### 3.3 端到端加密在节点之上

节点看不到内容：密钥交换在两端之间完成（QUIC 的 TLS 1.3，或 Noise），节点只转发密文。
`A7K2M9` 这种 6 位码**是地址，不是密码**——约 30 bit，绝不能当加密密钥用。

## 4. 编码设计（你问的「越少越好」到底能多小）

二进制布局 v1（小端），再整体用 **Crockford Base32**（大小写不敏感、去掉 `I L O U`，便于 OCR 与报障）：

| 字段 | 长度 | 说明 |
|---|---|---|
| version+flags | 1 B | 版本号 + 有无 v4/v6/域名、是否允许中转 |
| 地址 | 4 / 16 / 1+len | 四选一：IPv4 / IPv6 / 域名（用户常有域名，且 IP 变了码不用换，推荐域名） |
| 端口 | 2 B | 节点主端口 |
| 公钥指纹 | 8 B | 节点证书 SPKI 的 SHA-256 截断（64 bit，钉扎用；2^64 不可暴力） |
| 校验 | 1 B | CRC-8，输错时能明确说「码不对」而不是超时 |

实测长度（真算过，不是估）：

| 场景 | 字节 | Base32 字符 |
|---|---|---|
| 仅 IPv4 | 17 | **28** |
| 仅域名 `relay.example.com` | 30 | 48 |
| 仅 IPv6 | 25 | 40 |
| 双栈 IPv4+IPv6 | 33 | 53 |

**邀请串 = 节点编码 + 6 位门牌号**（定长拼接，不用分隔符，因为节点编码长度由版本决定，解析器知道从哪切）。
常见情况：`28 + 6 = 34` 字符；双栈域名场景 `48 + 6 = 54`。

诚实的取舍：
- **这些码不是给人手输的**，是复制粘贴/扫码用的。想手输必须砍掉指纹和 IPv6，那就不安全也不完整。
  **6 位门牌号仍然是人手输的那一个**——这是产品的核心手感，不能动。
- 指纹用 8 B 而不是 32 B，省掉约 22 个字符；安全性上 64 bit 钉扎够用（要伪造需 2^64 次哈希）。
- 如果你想让码更短，唯一有效的办法是**码里不带地址，只带一个短 ID**，那必然需要一个中心索引——
  与「不运营中心服务」直接冲突。所以现在的长度已经是这个模型的物理下限附近。

## 5. 必须先接受的 5 个代价

**① 新用户开箱即用需要一个「第 0 台」节点。**
节点同时是信令服务器，所以**没有任何节点就开不了房**（双方连候选地址都换不了）。
三个选项：
- (a) 仓库里放一份 `seed.json` 节点列表，条目指向社区自愿者/你自己的机器（你现在有 5 台 VPS）。开箱能用，但等于变相提供了服务，且要承担滥用与流量成本。
- (b) 完全空列表，用户必须自己粘贴一个节点编码才能用。最纯粹，但新手第一步就卡死。
- (c) 加一个「无节点模式」：双方手动交换候选地址（像手抄 WebRTC SDP）。零基建，但体验很差，只能当最后一招。
- **建议**：(a) 的弱化版——seed 列表存在，但每一行都标注来源、是否收费、是否记录流量；项目本身不承诺可用性。文档里说清楚「这是一份索引，不是我们的服务」。

**② 「Windows 也能当中继」在绝大多数家庭网里做不到。**
中继必须有**公网可达**的地址（公网 IP 或已做端口映射）。家宽 NAT 后面做不到，CGNAT 更做不到（移动网络基本必败）。
所以：
- Node 的**一等目标是 Linux VPS**（一键脚本 + systemd + docker）。
- Windows 版的价值是「有公网 IP 的少数人」与「同一局域网内直连」场景，**不能对用户承诺"装了就当中继"**。
- 安装脚本必须自己检测并明确警告：绑定的地址不可达 → 提示"你需要在路由器做端口映射，或换一台有公网 IP 的机器"。

**③ 「只打洞」的节点定位要说清。**
打洞失败不是边缘情况：对称 NAT、CGNAT、企业网/校园网封 UDP，失败率不低（具体数字必须在真机上测，别引用别家的）。
所以「不允许中转」的节点只能作为「连得上时更快」的补充，不能作为主路径。
产品口径建议：**门牌号默认就是"打洞优先 + 允许绕路"**，纯打洞节点是高级选项。

**④ 公开节点必然被滥用，密钥不是可选项而是准入机制。**
- 没有你发出的编码，连不上你的节点（编码里含指纹，节点校验），这是**唯一的准入**。
- 节点**从不主动外连任何目标**，只在「两个都持有有效编码的端点」之间转发 —— 所以它不是开放代理，这个性质要在文档里写死，也是它能安全开源的前提。
- 还需要：每 IP 限速、房间数上限、单房间带宽上限、`code_not_found` 查询限速（否则有人枚举 6 位码蹭服）。
- 开源后必然有人跑公开节点，随附一份 `docs/ABUSE.md`（怎么封人、怎么限流、日志留存多久）能省很多麻烦。

**⑤ UDP 被封的网络，连节点的 UDP 也走不通。**
企业网/校园网/部分酒店只放 443。所以节点最好同时提供 **TCP 443 入口**做兜底传输。
建议：**协议里留出 transport 字段，实现放到打完洞之后**，但接口现在就别写死成只能 UDP-only。

## 7. 7 态状态机与「是否中转？」的冲突，以及解法

AGENTS.md 定的是「打洞失败**自动**切中继」，你现在要「**问一下**是否绕路」。两者能共存，不必加第 8 个状态：

- 把「问不问」做成**连接前的偏好设置**：`总是自动中转` / `每次询问` / `从不中转`（默认自动，与 AGENTS.md 一致）。
- 偏好=每次询问时，打洞失败后 transport 停在 `punching`（用户看到「门有点难开，要绕路吗？」），
  并对外抛一个 **RelayOffer 事件**（不是状态）；用户点「绕路」→ 状态转 `relay`，点「不」→ 状态转 `failed(relay_unavailable)`。
- 这样「界面只渲染 state」的硬规矩不破，7 态不动，只是在 `punching` 上挂了一个待决策事件。

## 10. 讨论后的修正（2026-10-28，覆盖上文冲突条款）

### 10.1 已定

- **D1 节点只做 Linux。** 取消 Windows 节点版本。交付形态：一条安装命令（脚本 + systemd unit）+ 一条
  docker 命令。这同时消掉了 Windows 上的服务注册、WinDivert、防火墙配置三摊事。
  仍然保留对用户的能力检查：绑定地址不可达时明确报「这台机器没有公网可达地址」。
- **D2 列表的职责被修正：列表只负责「发现」，不负责「解析」。**
  节点编码是**自描述**的（地址+端口+指纹都在里面），所以一个刚建好的节点**不需要出现在任何列表里**
  就能被使用——房主把完整编码发给朋友即可，零等待。列表解决的是"我想找别人的节点/我想被别人找到"，
  这是发现需求，不是连通需求。原提案里"必须上列表拿 ID"把两件事耦合了，那等于重新引入中心依赖。
- **D3 三级邀请形态**（长度只在首次昂贵，首次是低频的）：

  | 形态 | 形态样例 | 长度 | 何时用 |
  |---|---|---|---|
  | 完整邀请 | `<节点编码><A7K2M9>` | ~34–60 | 首次配对；或对方没有该节点时 |
  | 短邀请 | `K7F2.A7K2M9` | **11** | 双方都已添加该节点（高频场景） |
  | 只有门牌号 | `A7K2M9` | 6 | 双方都只添加过一个节点时 |

  `K7F2` 是节点自选的 2 字节标签（编码里携带，Base32 后 4 字符），不是中心分配。
  解析规则：0 个匹配 → 「你还没有这个节点，让房主发完整邀请」；1 个 → 直接用；多个 → 列出让用户选。
- **D4 列表可插拔。** 三个来源合并：内置 seed、用户自定义列表 URL（JSON，静态托管即可）、手动添加。
  于是"某个人的节点想立刻被陌生人发现"也有解：**他自己托管一个列表，把 URL 发出去**，不必等官方列表。
  信任模型不变：身份靠编码里的指纹钉扎，列表被污染最坏是浪费时间，不构成中间人。
- **D5 打开列表不做任何主动探测。** 健康信息三级来源，从便宜到贵：
  1. 本地历史（每次真实使用记录的 RTT / 失败次数 / 最后成功时间）——最真实且零额外流量；
  2. 列表里自带的探测字段（由**列表发布者**的 cron 统一探测，标注时间戳）——流量集中在发布者 1 个 IP，
     而不是每个客户端各打一遍；
  3. 用户选中节点时的单次探测 + 手动「刷新」按钮。
  **拥挤度由节点在握手响应里自报**（`accepting` / `current_sessions` / `limits`），客户端缓存若干分钟。
  这样"满了"是连接时就知道的事实，不需要额外的健康接口，也不需要列表轮询。
- **D6 兜底传输：QUIC 主路 + TLS/TCP 443 兜底，上层帧协议共用。**
  `Link` 抽象 = 有序字节流；UDP 侧是 QUIC 流，TCP 侧是 TLS 1.3 流，上面跑同一套长度前缀帧。
  **否决 `udp2raw` / `phantun` 这一派「伪 TCP」方案**：它们要 raw socket / WinDivert，
  等于要管理员权限，与产品硬约束正面冲突。
- **D7 「是否绕路」做成设置偏好**（总是自动中转 / 每次询问 / 从不中转，默认自动），7 态不动。

## 11. 传输底座调研：有没有现成项目能直接用（2026-10-28）

要的能力清单：TCP 流 → UDP 打洞直连 → 打不通自动走节点转发 → 节点可自托管 → 身份可钉扎 → 客户端免管理员。

| 候选 | 打洞 | 节点可自托管 | QUIC/TCP443 兜底 | 身份模型 | 结论 |
|---|---|---|---|---|---|
| **iroh 1.4.1** | ✅ 内置 | ✅ `iroh-relay` 有独立二进制，支持 HTTP 或 HTTPS | ✅ 直连=UDP，中继=TLS/TCP（443 天然通） | Ed25519 `EndpointId`，TLS 无 CA，靠公钥认证 | **首选** |
| DIY（`quinn` + 自写信令） | 要自己写 NAT 探测/端口预测 | 自己定 | 自己写两套 | 自己定（能用 8B 指纹→码最短） | 备选，工作量被严重低估 |
| libp2p（DCUtR + Circuit Relay v2） | ✅ | ✅ | ⚠️ 中继也是自己的协议 | PeerId（multihash，编码后很长） | 过重，抽象层数多 |
| webrtc-rs 0.21 | ✅ ICE | ✅ TURN | ⚠️ ICE-TCP 支持弱 | DTLS 证书指纹 | SCTP 开销 + 兜底路径不硬 |
| tsnet（Tailscale 库） | ✅ | 要 headscale | ✅ DERP | 32B 节点密钥 | 引入协调服务器 = 又把中心装回来；且是 VPN 形状 |
| frp / rathole / ngrok 类 | ❌ 无 P2P | ✅ | — | — | 不符合"直连优先" |

### 11.1 为什么 iroh 几乎是为这个产品写的

`iroh` 的官方描述就是："暴露 QUIC 连接与流给上层，底层用**打洞**建立直连，直连不行时**自动**退回中继"。
逐条对上我们的需求：

- **打洞 + 中继一体**：与 ADR-0002 的"节点=信令+中继"完全同构。
- **中继只转密文**：文档原话是"中继只按 `EndpointId` 转发，无法解码内容"——正是我们"节点看不到流量"的要求。
- **中继协议就是 DERP 的改良版**：我们上一轮论证的形状，人家已经实现并验证。
- **`RelayMap` 就是一个"节点列表"数据结构**：直接对应客户端的节点列表 + 筛选。
- **中继可用 HTTP（不带证书）跑**：自托管节点没有域名也能用，正好配合我们"编码里带 IP+端口+指纹"的设计。
- **`iroh_relay::tls` 提供自定义 TLS 校验**：自签证书 + 指纹钉扎可做。
- **依赖里含 `portmapper`**：UPnP/NAT-PMP 自动端口映射已经内置——这是我们之前漏掉的**第三条路**（房主把端口自动映射出去，对方直接连，压根不用打洞）。
- **许可证 MIT OR Apache-2.0**：与我们的开源计划兼容。
- **已到 1.4.1**（2026-10-21），不是 0.x，API 有稳定性承诺，下载量 360 万+。

### 11.2 用它要付的代价（必须知道）

1. **身份是 32 字节 Ed25519 公钥**，不能截断成 8 字节——iroh 拨号必须拿全量 `EndpointId`。
   **但我们的邀请串本来就不需要放它**：邀请串里只放**节点**的身份，房主/房客的 `EndpointId`
   由节点的房间接口在"敲门"时交换。所以 28 字符的码仍然成立。**码短和用 iroh 不冲突。**
2. **节点变成两件事**：`iroh-relay` 二进制（Rust）+ 我们的房间/配额 API（Go）。
   systemd 管两个进程，安装脚本负责；好处是两者解耦，将来能换掉任一。
3. **`iroh-relay` 没有"信令但不搬运数据"的模式**。我们要的「只打洞 / 允许中转」开关，
   得自己加（fork 或在前置层拦）。这是真缺口，量不大但要算进工期。
4. **`iroh-relay` 没有按人限速/配额**。拥挤度、每房间带宽上限得靠
   ：OS 层 `tc`/`nftables` 按 IP 限速（糙但有效），或 fork 加计数器。**也影响"拥挤度自报"的实现方式。**
5. **引入一棵不小的依赖树**（rustls / axum / noq …），客户端二进制会变大——但 Tauri 本来就有壳，影响可接受。
6. **不要用它的默认中继（n0 的）和默认 DNS 发现**，否则等于又依赖了别人的中心服务。
   必须显式 `RelayMode::Custom(RelayMap)` 只装我们的节点，并关掉 `DnsAddressLookup`。

### 11.3 建议

- **传输底座 = iroh**，节点 = `iroh-relay` + 我们的 Go 房间/配额 API。
- **但第 3 步骨架完全不碰它**：状态机用假 transport 证明，接口立住之后再接 iroh。
  也就是说 ADR-0001 的 Go、ADR-0002 的节点模型都不用改，只新增 ADR-0003 定传输底座。
- 如果最终否决 iroh，代价要提前说清：DIY 意味着自己做 NAT 类型探测、端口预测、路径切换、
  中继协议、拥塞控制——**这是按周甚至按月计的调试工作，而且大部分时间花在"某种路由器下不工作"上**。

### 11.4 第三条路：UPnP / NAT-PMP 自动端口映射（之前漏了）

房主侧如果能自动把 UDP 端口映射出去，对方**直接连**，根本不用打洞，
成功率接近 100%（只要路由器支持 UPnP/NAT-PMP/PCP）。不成功也只是回落到打洞，零成本。
**建议：房主开门时先试端口映射，"门开了"的直接程度显著提升。** 客户端不需要管理员权限。
在状态机里它不算新状态——映射成功也归入 `direct`，UI 只说"门开了"。

## 12. 公共节点列表（定稿）

形式：**仓库里的一个静态 JSON + PR 提交**，不跑服务。字段：

```json
{
  "id": "K7F2QA9M",            // 节点公钥指纹前缀，自证
  "name": "东京 · 某人",
  "relay": true,               // 是否允许数据中转
  "endpoints": ["relay.example.com:443", "[2001:db8::1]:443"],
  "limits": { "max_sessions": 50, "per_room_bps": 2000000 },
  "note": "免费，别跑大流量"
}
```

四条规则：

1. **`id` 必须自证。** `id` = 节点 Ed25519 公钥指纹的前 8–10 字符；客户端连上后校验指纹与 `id` 一致，
   不一致就**直接断开并报「节点被替换」**。→ 列表被篡改最多是无用，不能冒名。这是列表**不需要签名**的原因。
2. **列表只放静态能力，不放运行状态。** 状态（延迟/占用/满没满）由客户端探测与节点自报获取。
3. **国内访问 GitHub raw 不稳。** 客户端内置一份快照 + 支持镜像 URL（jsDelivr / 自建 / 任意静态托管）+ 自定义列表 URL。
4. **公开发布 = 公开你的 IP。** 必须显式勾选；允许只发布域名；列表页写明风险。

私密节点：不进列表，走完整编码 + 邀请码。两条路径最终都落到"一条带指纹钉扎的节点记录"，解析逻辑只有一份。

## 13. 探测策略（定稿）

只展示不打扰：**打开列表不发任何包**。用户点「刷新」才真探，探的是**当前可见列表**。

- **探针 = 一次握手 hello**（顺带拿回能力、实时占用、带宽上限），不做第二套健康接口。
- **防反射放大是硬要求**：请求带 nonce，响应 ≤ 请求大小。否则节点会被拿去当 DDoS 放大器。
- 并发上限 5–8、超时 1.5s、**负缓存 5 分钟**（防用户狂点刷新）。
- 按本机网络栈过滤：纯 IPv4 用户不去测 IPv6 节点。
- 拥挤度分两层：**静态配额**（节点配置：最大会话、每房间带宽）+ **实时占用**（当前会话数/带宽），
  后者由握手返回、客户端缓存若干分钟。

## 14. AGENTS.md 产品边界修订稿（待你确认）

原文"不装虚拟网卡、**不要管理员权限**"要拆成两句话，否则它会跟"节点要开端口、要限速"打架：

- **客户端（玩家侧）仍然不要管理员权限**——这是产品对用户的核心承诺，不能动。
- **节点（服务端）以 root 装成 systemd 服务**，允许做网络侧操作（监听端口、防火墙、限速）。
- **仍然不接 TUN、不做网段**——这条不变，它是"联机工具 vs VPN"的分界线。
- **仍然只代理 TCP `25565`（端口可改），一个房间一条通道**——不变。

按这个拆分：`udp2raw`/`phantun` 那套"伪 TCP"在**客户端仍然禁用**（要 WinDivert = 管理员），
但在**节点侧是允许的**（root 环境，可以用 raw socket 做 443 伪装路线）。

## 15. 列表的自动审核（CI 设计）

没有现成产品做这件事，但 GitHub Actions 够用。关键是**「id = 公钥指纹」让审核变成可验证的事实检查，
而不是格式检查**。

### 15.1 CI 校验什么（按顺序）

1. **格式**：JSON schema、`id` 匹配 `^[0-9A-Z]{8}$`、endpoint 合法、端口 1–65535、字段长度上限。
2. **唯一性**：`id` 不重复、endpoint 不重复。
3. **id 自证（核心）**：runner 真连一次节点，取回节点公钥，校验其指纹前缀 == `id`。
   这一条同时证明了「节点活着」与「这个 id 属于提交者」——**抢注 id 在数学上不可能**。
4. **能力一致**：节点自报的 `relay` 标志必须与列表条目一致（防止"写着允许中转、实际不转"）。
5. **稳定性**：连探 3 次取中位数，避免单次抖动导致误判。
6. **结果回帖**：bot 把 v4 RTT / v6 RTT / 是否允许中转 / 当前占用贴回 PR，维护者一眼看完。
7. 通过后打 `node-verified` 标签 + required status check 绿。**不自动 merge**——列表是信任边界，合并留给人和 CODEOWNERS。

### 15.2 安全红线（这一节比上面所有条都重要）

PR 里的地址会被 runner 主动连接，等于**把 CI 当端口扫描器**。必须：

- **拒绝非公网地址**：私有段、环回、链路本地、以及云元数据地址（`169.254.169.254`、阿里云 `100.100.100.200`、
  AWS IPv6 `fd00:ec2::254` 等）。这是防 SSRF，不是洁癖。
- **绝不用自托管 runner 跑 PR**：自托管 runner 通常在自己内网，一个恶意 PR 就能让它去打你的内网和元数据服务。
  用 GitHub 托管的临时 runner（公开仓库免费）。
- 探测限速 + 超时 + 总时长上限。
- fork 来的 PR 默认只读 token，不要给它 `pull_request_target` 权限去 checkout 代码再执行。

### 15.3 提交体验

- **Issue Form → Actions 生成 PR**：让人填表单（名称/域名/IP/是否允许中转/上限），bot 转成 JSON 并直接跑校验。
  比让人手写 JSON 正确率高一个数量级。
- 节点二进制带 `knock-node publish`，本地生成带自签证明的提交片段，进一步降低出错。

### 15.4 列表质量主要靠巡检，不靠入门审核

入门审核只保证「提交那一刻是好的」。真正的质量来自 **cron 巡检**：

- 定期对列表里所有节点跑同一套检查；
- 连续失败 N 天 → 自动开 issue 并打 `stale`；
- 再 N 天 → 移出列表（开 PR，仍走人的确认）。

### 15.5 验证器必须复用客户端的探测代码

CI 与客户端共用**同一个 `probe` 模块**（同一个 crate / 同一份 Go 包），否则会出现
「CI 通过但客户端连不上」——这种不一致比没有审核更糟。
